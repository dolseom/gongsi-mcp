# 참고 MCP(`korean-dart-mcp` v0.6.0) 흡수 사항

> 정리: 2026-07-29 · 대상: `(참고)소스/dart-mcp-design-reference.zip` (Python 소스 전량 + 설계 레퍼런스 + CHANGELOG/PROGRESS)
> 원 프로젝트: OpenDART 투자·재무 관점 MCP, 도구 8개, pytest 116 통과, 팀 배포 v0.5.0 / 소스 v0.6.0
> 본 문서 목적: **우리(gongsi-mcp)가 무엇을 그대로 가져오고, 무엇을 고쳐 가져오고, 무엇을 버리는지**를 근거와 함께 고정

원 프로젝트가 3개월간 **실측으로 비싸게 배운 것**이 자산의 본체다. 코드보다 그 판단 근거를 가져온다.

## 0. 한 줄 요약

우리는 룰 엔진(M1)까지 왔고 M2에서 DART 클라이언트·검색을 만든다.
참고 MCP는 정확히 그 지점에서 **7번의 recall 사고와 성능 사고**를 겪고 해결한 코드다.
→ 클라이언트/검색 레이어는 **참고 설계를 기본값으로 채택**하고, 우리 도메인(공정위 J공시)에 맞게 조정한다.

## 1. 그대로 가져올 것 (검증된 설계)

### 1-1. 검색 정확도 — 이게 가장 값지다

| # | 규칙 | 근거(실측) | 우리 적용 |
|---|---|---|---|
| A1 | **dedup 키는 `rcept_no` 단일** | 복합키 `(corp_code, rcept_dt, report_nm)`로 "강화"했다가 1년 41건 → 33건, **8건 누락**. 같은 회사·같은 날 동일 보고서명 다중 제출이 정당하게 존재(행복나래 8건, 진천테크노 4건 등) | `audit_group_disclosures`·`track_internal_transactions` 전부 동일. **절대 복합키로 개선하지 말 것** |
| A2 | **`max_pages` 상한 넉넉히(100)** + `total_page` 기반 조기 종료 | 기본 10일 때 B 카테고리가 90일당 12~16페이지라 조용히 잘림. 33건 → 41건(웹 화면과 일치). 회복 사례: 토파스여행정보·에스케이스토아·에코에너지솔루션·세광패션 | J 카테고리도 90일당 ~30페이지(우리 실측 2주 470건). **상한 100 필수** |
| A3 | **`report_nm`은 클라이언트 사이드 부분일치** | OpenDART가 서버 필터를 지원하지 않음 | 프리셋·보고서명 필터 전부 응답 후 필터 |
| A4 | **recall 검증 윈도우는 1년 이상** | 10일 윈도우로 "recall 100%" 결론 냈다가 1년에서 뒤집힘(false negative). 6개월도 부족했음 | 우리 회귀 테스트 기준선도 1년 윈도우로 |
| A5 | **"카테고리 X만으로 충분"은 X vs ALL 실측 count 비교로만 확정** | 추론으로 판단한 게 두 번 다 틀림 | §3 참조 |

### 1-2. 성능·안정성

| # | 규칙 | 근거 | 우리 적용 |
|---|---|---|---|
| B1 | **적응형 날짜 분할** (균등 90일 금지) | 3년=13청크 균등분할 시 J는 청크당 1,500~3,000건=30~90초 → per-task timeout 전멸. 실제 신고는 2월·8월(결산·주총)에 집중되므로 **균등 분할은 구조적으로 틀림** | `mode:"batch"` 전수 수집에 그대로 필요 |
| B2 | 분할 시 **측정 호출 예산 가드** (`100 + 50×카테고리수`) | 최악 이진트리는 단일 403 / ALL 4,030 호출 | 예산 초과 시 30일 균등 fallback(원청크 유지 아님 — 폭주 재발) |
| B3 | 측정 실패는 **예외별 분기** | 네트워크 오류 → 분할 시도 / API 오류·rate limit → 원청크 유지(더 쪼개면 호출만 증가) | 동일 |
| B4 | **per-task 타임아웃으로 부분 결과 보존** | 클라이언트 레벨 단일 timeout은 전체 abort → 부분 결과 전멸. task 단위 격리 + `Promise.allSettled` | 계열사 수십 개를 도는 우리 감사 도구에 필수 |
| B5 | **connect/read 타임아웃 분리** (10s / 100s) | 단일 30s일 때 16페이지 호출이 27.34초 → margin 2.66초. read만 늘리고 connect는 짧게(끊김 빠른 감지) | 동일 |
| B6 | 동시성 변경 효과는 **wave 수**(`ceil(task/동시성)`)로 계산 | 5→7은 wave 수 동일해 효과 0. 5→10이라야 2 wave → 1 wave | 동일 |

### 1-3. 호출량·한도 관리

| # | 규칙 | 근거 | 우리 적용 |
|---|---|---|---|
| C1 | **KST 일별 호출 카운터 영속화** | OpenDART 한도 리셋이 KST 자정 기준. 20,000건/일 | DART·포털 각각 카운터 |
| C2 | 경고(18,000) / **하드스톱(19,000)은 본문 다운로드만 거부**, 목록 조회는 허용 | 목록까지 막으면 도구가 통째로 죽음 | 동일 |
| C3 | 카운트 증가는 **실제 응답 수신 1회** (재시도는 성공분만) | | 동일 |
| C4 | DART status → 예외 매핑: `013` 빈결과 정상화 / `020` rate limit / `021` 메시지 보강 | | PRD 6.3의 status별 안내와 통합 |
| C5 | 재시도는 `429`/`5xx`/네트워크만, 백오프 `min(2^n, 8)`초, 최대 3회 | | 동일 |

### 1-4. 원문·ZIP 처리 (우리 `read_disclosure`에 직결)

| # | 규칙 | 근거 |
|---|---|---|
| D1 | ZIP 응답은 **`PK` magic 검사 먼저**, 아니면 JSON/XML 오류 페이로드에서 status/message 추출 | DART는 오류를 200 + JSON으로 준다 |
| D2 | **파싱 실패 본문도 빈 값으로 캐시** | 같은 공시 반복 다운로드 방지 |
| D3 | ZIP 내 텍스트 후보(`.xml/.html`) 중 **가장 큰 것**을 본문으로, 바이너리만 있으면 `body_parsable=false` + `attachment_types` 반환 | HWP 첨부만 있는 공시 존재 |
| D4 | **XML 폭탄 방어** — 30MB 초과 XML은 파싱 거부 | DoS |
| D5 | ZIP 안전검사 — 파일수 500 / 해제총량 100MB / 압축률 1000:1 / 경로 탈출(`..`·절대경로·드라이브·NUL) 거부 | zip bomb·path traversal |
| D6 | **HTML은 반드시 디코딩된 문자열로 파서에 전달** | 파서가 meta charset 없으면 ISO-8859-1로 가정해 한글을 깨뜨림 |
| D7 | 인코딩 감지 후 디코딩(EUC-KR/UTF-8 혼재), 실패 시 정규식 태그 제거 폴백 | |

> 우리 J001 원문은 **UTF-8 정형 XML**로 확정(M0)이라 D6·D7 부담은 낮다. 다만 **첨부(HWP)** 경로에서는 그대로 유효하다.

### 1-5. 응답 설계 (LLM이 읽는 계약)

| # | 규칙 | 근거 |
|---|---|---|
| E1 | 모든 검색 응답에 **`diagnostics` 블록** — `partial_results` / `calls_consumed` / `dedup_dropped` / 분할 진단 | LLM이 "이 결과가 완전한가"를 판단할 수 있어야 함. 우리 감사 도구는 **불완전 결과를 완전한 것처럼 보고하면 그게 최대 리스크**(PRD §11) |
| E2 | **`compact` 모드** — `schema` 헤더 + 값 배열, 파생 가능한 필드(viewer_url) 제외 → 토큰 30~40% 절감 | |
| E3 | **에러 응답 규격 통일**, 도구는 예외를 밖으로 던지지 않는다 | MCP 클라이언트에 스택트레이스 노출 방지 |
| E4 | **예외 메시지·로그에 API 키 절대 노출 금지** — 회귀 테스트로 고정 | 실제 사고 있었음(`crtfc_key`가 예외 문자열에 포함) |
| E5 | **stdout은 MCP 프로토콜 전용**, 로그는 stderr + 회전 파일 | stdio 서버 필수 조건 |

## 2. 고쳐서 가져올 것 (우리 PRD와 충돌)

### 2-1. ★ MCP 클라이언트 ~60초 한계 — 아키텍처 급 이슈

참고 프로젝트 v0.5 통합 테스트 실측:

| 조건 | 결과 |
|---|---|
| corp_code 지정 검색 | 정상 |
| J 카테고리 6.5개월 1회 | 성공 (14,600건) |
| J 카테고리 3개월 × 12회 | 11/12 성공 (91.7%) |
| **J 카테고리 1년 1회** | **timeout (~68초)** |
| **2026-02~05 3개월(결산·주총 시즌)** | **timeout (66초)** |

서버 내부 per-task 180초를 늘려도 소용없다. **클라이언트가 약 60초에 끊는다.**

> **우리에게 직격탄**: `audit_group_disclosures`(킬러 #2)는 계열사 수십~수백 개 × 기간 × 원문 파싱을 도는 도구다. 60초 안에 끝날 수 없다.

**✅ 결정(2026-07-29): M2 = 사전 예측 + 분할 안내, M3 = `continuation_token`**

| 단계 | 방식 | 시점 |
|---|---|---|
| ① | **범위 사전 예측 + 분할 안내** — 측정 호출 1회로 대상 규모를 재고, 60초 초과 예상이면 즉시 반환 | **M2** |
| ③ | **per-task 타임아웃 + `Promise.allSettled`** 부분 결과 보존(`partial_results=true`) | **M2** (①과 병행) |
| ② | `continuation_token`으로 이어받기 — 한 호출은 항상 60초 안에 끝나고 남은 범위를 토큰으로 반환 | M3 (정공법) |
| ④ | 백그라운드 잡 + 폴링(`start_audit`/`get_audit_result`) | 미채택 — 상태·수명주기 관리로 M2가 과중해짐 |

①의 응답 형태:

```json
{ "error": "range_too_large",
  "message": "계열사 67개 × 12개월은 한 번에 처리할 수 없습니다.",
  "estimated_seconds": 210,
  "suggested_splits": [{"from":"20260101","to":"20260331"},
                       {"from":"20260401","to":"20260630"}] }
```

①이 가장 싸게 "도구가 그냥 죽는" 사고를 막는다. 참고 프로젝트는 이걸 코드가 아니라 **운영 룰(2~3개월 윈도우 권장)로만 회피**했는데, 우리 감사 도구는 회피가 불가능하므로 서버가 스스로 판단해야 한다.

### 2-2. 공시 목록 캐시 — PRD 6.3 수정 필요

- PRD 현재: "공시검색 **1시간**" 캐시
- 참고 프로젝트: **목록은 절대 캐시하지 않는다**(신선도). 캐시 대상은 본문·corps·호출카운터·watch 상태뿐

우리 사용자는 공시담당자다. "방금 접수된 공시"가 안 보이면 도구를 신뢰하지 않는다.
→ **목록 캐시 제거 또는 수 분 단위로 축소**. 본문·corp_code·기업집단 구조(연 1회 갱신)는 기존 TTL 유지.

### 2-3. 균등 90일 분할 — PRD 5.5 수정 필요

- PRD 현재: `mode:"batch"` = "90일 자동분할 전수 수집"
- → **적응형 분할**(§1-2 B1)로 교체. 균등 분할은 결산·주총 시즌에 구조적으로 실패한다.

### 2-4. SQLite 선택 — `better-sqlite3` 재검토

| 항목 | 참고 프로젝트 | 우리 |
|---|---|---|
| 엔진 | Python 내장 sqlite3, **3.34+ 강제** (FTS5 `tokenize='trigram'` 한글 부분일치) | PRD는 `better-sqlite3` |
| 문제 | — | 네이티브 빌드 → `npx setup` 마찰(윈도우 빌드툴), Node 버전별 prebuilt 의존 |

우리 배포 전략이 `npx setup` + 플러그인 마켓플레이스라 **네이티브 의존성은 설치 실패의 1순위 원인**이다.

**✅ 결정(2026-07-29): `node:sqlite` 채택, `engines >= 22.5`**

실측으로 선택지가 정리됐다:

```
Node v24.13.0
node:sqlite 사용 가능 / SQLite 3.50.4
FTS5 tokenize='trigram' 한글 부분일치: 지원 → "대규모[내부거래] 이사회 ..."
corp 인덱스 118,543건 순수 JS Map: 30.1 MB
```

| 안 | 판정 |
|---|---|
| `better-sqlite3` | ❌ 네이티브 빌드 → `npx setup` 설치 실패 1순위. 참고 프로젝트가 배포 마찰로 고생한 것과 같은 종류 |
| **`node:sqlite`** | ✅ **채택.** 의존성 0으로 참고 MCP 요구 조건(SQLite 3.34+ trigram)을 그대로 충족. Node 20 포기는 실익 없음(2026-04 EOL) |
| JSON + Map | 예비안. 30.1MB로 corp 인덱스는 충분하나 원문 검색을 포기해야 함 |

⚠️ `node:sqlite`는 아직 experimental API다 → **얇은 어댑터로 감싸** 교체 가능하게 두고, `ExperimentalWarning`이 stdout을 오염시키지 않게 한다(stderr 전용).

### 2-5. `report_nm` prior 매핑 → 우리는 **프리셋**이 그 역할

참고 프로젝트는 보고서명으로 카테고리를 추정하는 매핑 dict를 수동 유지했다(운영 부담으로 명시됨).
우리는 `preset: "ftc_all" | "internal_transaction" | ...`으로 **사용자가 의도를 직접 주는 구조**라 추정이 불필요하다. 매핑 dict는 가져오지 않는다.
다만 **`prior_applied` 같은 "전체 검색이 아님" 표시**는 프리셋에도 그대로 필요하다 → `diagnostics`에 `preset_resolved`(실제 조회한 코드 목록)를 넣는다.

### 2-6. 환경변수 접두사

참고 프로젝트는 config에 `CONCURRENCY`/`PER_TASK_TIMEOUT`을 썼는데 코드는 `DART_MCP_` 접두사만 읽어 **3개 값이 조용히 무시되고 있었다**(실사용 config에서 확인됨).
→ 우리는 접두사 통일 + **기동 시 미인식 env 경고 로그**를 낸다.

## 3. J 카테고리 recall — 참고 문서의 결론을 우리 실측으로 검증

**참고 문서가 가장 강하게 경고하는 항목**이자, 우리 프로젝트의 근본 전제(`pblntf_ty=J` / `J001~J009` 전수 수집)를 직접 겨냥한다.

### 3-1. 참고 문서의 주장

> v0.2.0 BREAKING: 기본값 `J` → `ALL`.
> "`rm="공"` 마커가 붙은 공정위 제출분이 카테고리상 J가 아닌 B/E 등에 등재되는 케이스 다수. 1년 실측 v0.1 recall ~50%(21/41).
> 결정적 증거: 현대아이이씨(`20260227007143`, `rm="공"`)가 `pblntf_ty="J"` 필터에서 누락."

### 3-2. 그런데 같은 프로젝트의 후속 실측이 이를 뒤집는다

CHANGELOG v0.2.1 / v0.4.0을 붙여 읽으면 시간순 사실은 이렇다:

| 버전 | 조건 | 결과 |
|---|---|---|
| v0.1 | J 단독 + **`max_pages=10`** | 21건 |
| v0.2.0 | ALL + **`max_pages=10`** | 33건 |
| v0.2.1 | ALL + **`max_pages=100`** | **41건** (웹 화면 일치) |
| v0.4.0 | **B 단독** + `max_pages=100` | **41건** — 그리고 *"1년 윈도우 실측 **B = J = ALL = 41건**"* 으로 J 호출을 redundant 판정해 제거 |

→ **v0.4.0 시점에 J 단독으로도 41건 전부 나온다는 것이 원 프로젝트 자체 실측으로 확인됐다.**
v0.1의 recall 50%는 **카테고리 필터가 아니라 `max_pages=10` 페이지 절단**이 원인이었다고 보는 게 정합적이다.
J 카테고리는 90일당 30페이지 규모라 상한 10에서 심하게 잘린다. 현대아이이씨 누락도 같은 원인으로 설명된다.

> **문서의 §6-2 요약("J는 recall 50%")은 원인을 잘못 귀속한 서술이다.** 그대로 믿고 우리 설계를 ALL로 바꾸면 호출량이 10배가 되고 60초 한계에 그대로 부딪힌다.

### 3-3. 우리 실측 — 2주 윈도우 (2026-07-01 ~ 07-14)

`last_reprt_at=N`, `max_pages` 충분, 전체 공시 7,142건 전수 수집 후 대조:

| 항목 | 건수 |
|---|---|
| `pblntf_ty=J` | **470** |
| `J001~J009` detail 합집합 | **470** (J001 363 / J004 19 / J005 68 / J008 2 / J009 18) |
| 전체 공시 중 `rm`에 "공" 포함 | **470** |
| **`rm="공"`인데 J로 안 잡히는 건** | **0** |
| **`rm="공"`인데 J001~J009로 안 잡히는 건** | **0** |
| J인데 `rm`에 "공" 없는 건 | 0 |

→ 이 윈도우에서는 **`pblntf_ty=J` ≡ `J001~J009` ≡ `rm="공"`** 이 완전히 일치한다.
→ **J002·J003·J006·J007이 0건인 것은 "다른 카테고리로 샜다"가 아니라 실제로 해당 유형 제출이 없다**는 뜻이다.

### 3-4. ★ 결산·주총 시즌 전수 대조 + "결정적 증거" 직접 검증 (2026-02-23 ~ 03-06)

짧은 윈도우의 false negative를 피하려면 **신고가 폭주하는 구간**을 봐야 한다. 참고 프로젝트가 timeout을 겪은 바로 그 시즌이고, 그들의 결정적 증거(현대아이이씨, 2026-02-27)가 이 구간에 들어 있다.

전체 공시 **14,597건** 전수 수집 후 대조:

| 항목 | 건수 |
|---|---|
| `pblntf_ty=J` | **3,505** |
| `J001~J009` detail 합집합 | **3,505** (J001 216 / J004 3,206 / J005 67 / J008 10 / J009 6) |
| 전체 공시 중 `rm`에 "공" 포함 | **3,505** |
| **`rm="공"`인데 J로 안 잡히는 건** | **0** |
| **`rm="공"`인데 J001~J009로 안 잡히는 건** | **0** |
| J인데 `rm`에 "공" 없는 건 | 0 |

**참고 프로젝트의 결정적 증거 직접 조회** — `rcept_no=20260227007143`:

```
회사=현대아이이씨  보고서=증여결정  rm=공  접수일=20260227
pblntf_ty=J 로 잡히는가       : ✅ 잡힘
J001~J009 로 잡히는가         : ✅ 잡힘
실제 등재 카테고리(당일 sweep): [B, J]   ← J에도 정상 등재되어 있다
```

> **참고 문서가 "J 필터에서 누락된다"고 지목한 바로 그 공시가, J 필터로 정상 조회된다.**
> 그 공시는 B와 J **양쪽에 등재**되어 있다. 참고 프로젝트가 v0.1에서 이걸 놓친 건
> `max_pages=10` 절단 때문이다 — 이 시즌 J는 2주에 3,505건(=36페이지)이라 상한 10이면 **70% 이상이 잘린다.**
> v0.1의 "recall 50%"와 자릿수가 맞는다.

### 3-4b. 유일하게 남은 반증 기록도 소멸 (v0.2.1 누락 4개사 재조회)

Codex 교차검토가 참고 소스에서 반증 후보 한 건을 찾아냈다. `PROGRESS.md:229`:

> "카테고리 probe (각 rcept_no를 A~J 카테고리별 sweep): 모두 **B(주요사항보고) 카테고리**에 등재 (**3개사는** B+J 양쪽)"

4개사 중 **1개사는 B-only**였다는 서술이다. 사실이면 J 전수설의 반례가 된다. 그 4개사를 직접 조회했다:

| 회사 | rcept_no | 등재 카테고리 | detail | J 포함 |
|---|---|---|---|---|
| 토파스여행정보 | 20260211000686 | `[B, J]` | `J005` | ✅ |
| 에스케이스토아 | 20260209000083 | `[B, J]` | `J005` | ✅ |
| 에코에너지솔루션 | 20260130000020 | `[B, J]` | `J005` | ✅ |
| 세광패션 | 20260129000298 | `[B, J]` | `J005` | ✅ |

`last_reprt_at` Y/N 어느 쪽으로 조회해도 동일하다. **4개사 전부 J에 등재되어 있다.**
→ 참고 프로젝트의 당시 probe 기록이 부정확했던 것으로 판단된다(그 probe 자체도 절단 영향을 받았을 가능성이 높다).
→ **max_pages 절단 귀속을 반박할 근거가 참고 소스에 더 이상 남아 있지 않다.**

> 부수 확인: "증여결정"은 detail 코드상 **J005(비상장사 중요사항)** 로 분류된다. 우리 J005 매핑과 일치한다.

### 3-4c. ★ `last_reprt_at` — 우리 감사 도구를 무너뜨릴 뻔한 발견

Codex가 "J와 ALL 양쪽에 동일 적용되므로 카테고리 비교에는 영향 없지만 **전수 여부에는 별도 위험**"이라고 지적한 항목이다. 실측했다(2026-02-23~03-06):

| 조회 | `last_reprt_at=N` | `last_reprt_at=Y` | N에만 | Y에만 |
|---|---|---|---|---|
| 전체 공시 | 14,597 | 12,794 | **1,803 (12.4%)** | 0 |
| `pblntf_ty=J` | 3,505 | 3,430 | **75 (2.1%)** | 0 |

- **`Y`는 `N`의 진부분집합**이다. Y가 추가로 주는 건 하나도 없다.
- N에만 있는 J 75건의 `rm`은 **`공정`**(공정위 제출 + 정정) — 정정으로 대체된 **원본 제출분**이다.
  예: 미래에셋캐피탈 `특수관계인에대한출자`, 솔라시도삼호 `특수관계인으로부터자금차입`, 한화자산운용 `특수관계인과의수익증권거래`

> **우리에게 치명적인 이유**: `audit_group_disclosures`의 핵심 판정이 **"이사회 의결일 대비 원본 접수일이 기한을 넘겼는가"** 다.
> `last_reprt_at=Y`로 조회하면 **원본이 사라지고 정정본만 남아** 원래 접수일을 알 수 없다 → **지연 판정이 원천적으로 불가능**해진다.
> 게다가 J004는 정정률 91%(M0 실측)라 정정 추적 자체가 `draft_disclosure`의 근거다.
>
> **참고 프로젝트는 `last_reprt_at="Y"`를 기본값으로 하드코딩했고 오케스트레이터가 이를 바꾸지 않는다**(`dart_api.py:287`).
> 그들은 투자·재무 관점이라 최종본만 봐도 되지만, **우리는 정반대다.**
> → **우리 기본값은 반드시 `N`.** 도구 인자로 노출하되 감사·기한 판정 경로에서는 `N`을 강제한다.

### 3-5. 우리 결론 (확정)

- **`J001~J009` 전수 수집 전제는 유지한다.** ALL 합집합으로 바꾸지 않는다.
  두 개의 독립 윈도우(평시 2주 7,142건 / 시즌 2주 14,597건) 전수 대조에서 **누락 0**, 그리고 참고 프로젝트의 반례가 직접 반증됐다.
- 단, **`max_pages`를 넉넉히(100) 두는 것이 필수 조건**이다. 이것이 참고 프로젝트가 recall 사고로 배운 진짜 교훈이고,
  그들 자신은 그 교훈을 카테고리 문제로 잘못 귀속했다.
- **`rm`에 "공" 포함은 J의 신뢰할 만한 동치 마커**다(양방향 일치 확인). `공정`(공+정정) 같은 복합 마커가 있으므로 **완전일치가 아니라 포함 검사**로 판정한다.
  방어 장치로 감사 도구에 **`rm` 교차검증**을 넣는다 — 수집 결과에 `rm`에 "공"이 없는 건이 섞이거나, 다른 경로에서 J 밖 `rm="공"`이 발견되면 `diagnostics`에 경고를 띄운다.
  이 경고가 실제로 뜨면 그때 ALL 합집합 전환을 재검토한다.
- **`last_reprt_at=N` 고정** (§3-4c). Y는 원본 제출분을 지워 지연 판정을 불가능하게 만든다.
- ALL로 바꿨을 때의 비용: 호출량 10배 + 60초 벽 직격(§2-1). **얻는 것이 없고 잃는 것만 있다.**

**⚠️ 단, "`max_pages`만 넉넉히 두면 된다"는 과한 요약이다.** Codex 교차검토가 지적한 대로, 참고 소스 코드에는 **절단과 독립적인 누락 경로**가 더 있고 우리도 그대로 물려받는다:

| 누락 경로 | 내용 | 우리 대응 |
|---|---|---|
| **조용한 절단은 여전** | `while page <= max_pages` 종료 후 `total_page > max_pages`인지 **표시도 예외도 없다**(`dart_api.py:370`). 100도 부족한 청크가 있으면 같은 사고가 재발한다 | **`truncated: true` + 실제 `total_page`를 `diagnostics`에 반드시 노출.** 상한을 올리는 것보다 이게 본질 |
| **청크 실패의 조용한 부분 반환** | 청크 예외가 `categories_failed`에만 기록되고 결과는 그대로 반환된다. 실제로 `J + 3년 → 14/14 TimeoutError, hits=0` 사례가 문서에 있다 | `partial_results=true`를 **감사 도구가 판정 결과에 그대로 전파**. 불완전 수집 위에서 "누락 없음"을 결론내면 안 됨 |
| **페이지 경계 이동** | 페이지마다 실시간 재요청(`sort=date desc`)이라 수집 중 신규 접수가 삽입되면 밀림이 생긴다 | 과거 확정 구간만 감사 대상으로 삼고, 최근 구간은 경고 표시 |
| **적응형 분할 결과가 조건마다 다름** | 측정 기준이 달라지면 청크 크기·timeout 위험이 달라진다 | 분할 결과(`date_chunks`)를 응답에 노출해 재현 가능하게 |
| **`last_reprt_at` 기본값** | 참고 소스는 Y 하드코딩 | N 고정 (§3-4c) |

- 회귀 테스트 기준선을 **1년 윈도우**로 만들어 고정한다(§1-1 A4). 위 검증들은 2주 × 2구간(총 28일)이라 아직 A4를 충족하지 않는다 —
  M2에서 1년 기준선을 한 번 만들어 박아둔다. 또한 `J ≡ J001~J009 ≡ rm=공`은 **실측된 경험적 등식이지 코드가 보장하는 불변식이 아니다**(오케스트레이터는 `pblntf_detail_ty`를 아예 전달하지 않는다).

## 5. 원 프로젝트가 남긴 미해결 과제 (우리가 상속)

1. **클라이언트 60초 한계 대응** — §2-1. 원 프로젝트는 "운영 룰(2~3개월 윈도우 권장)"로 회피만 했다. 우리는 감사 도구 때문에 회피가 불가능하다.
2. **per-category 날짜 분할** — 현재는 max-of-categories라 J 때문에 다른 카테고리도 과분할된다. 우리는 J만 쓰므로 **이 문제 자체가 없다**(우리 구조의 이점).
3. **2단계 본문 다운로드 병렬화** — 원 프로젝트는 순차. 우리는 처음부터 병렬(세마포어)로 간다.
4. **prior 매핑 자동 학습** — 우리는 프리셋이라 해당 없음.
