## 방법

- 스크립트: `scripts/measure-recall-baseline.mjs` — **프로덕션 수집 경로(`collectAdaptive`) 그대로** 사용.
  별도 수집기를 만들어 재면 우리 코드의 recall 이 아니라 측정기의 recall 을 재게 된다.
- 기간 고정: **2025-08-01 ~ 2026-07-31**. `rcept_dt`(접수일)는 과거로 소급 추가되지 않으므로
  이 기간의 수치는 언제 재측정해도 같아야 한다 → 회귀 기준선으로 성립.
- 창 구성: 2개월 × 6개 (corp_code 없는 검색·측정은 3개월 초과 시 status 100 — 함정 10번).
- 대조 기준: 각 창에서 DART 가 신고한 `total_count` 합계 vs 실제 수집한 고유 `rcept_no` 수.
- 회귀 테스트: `test/recall-baseline.test.ts` + `test/fixtures/recall-baseline-2026.json` (오프라인 —
  기준선 계약을 고정. 실제 재측정은 스크립트 수동 실행).

## 완전 수집까지의 시행착오 — 같은 벽에 다시 부딪히지 말 것

1. **1차 (2026-08-13 새벽)**: 결산시즌 대형 청크 6개가 per-task 180초 타임아웃으로 실패 → 85.3%.
   `partial_results=true` 로 정확히 보고됐다 (korean-dart-mcp 피드백 §2-1 ②가 경고한 사고 유형의
   방어가 실전 작동한 첫 사례). → threshold 500 + perChunkTimeoutMs 15분으로 해소.
2. **2차 (2026-08-13 밤 1회차)**: 타임아웃은 해소됐지만 **단일 일자 청크가 maxPages 상한에 걸렸다** —
   20260401 접수분 13,586건 = 136페이지 > 기본 상한 100. 날짜로는 더 쪼갤 수 없는 청크라 분할이
   무력하고, `truncated=true` 로 정직 보고됐다 (함정 0번 "100도 부족한 청크가 나오면 재발"의 실측 사례).
   j_not_in_all 23건이 전부 이 구간이었다. → **`GONGSI_MAX_PAGES=150`** 으로 완전 수집.
3. **재측정 중 발견된 신규 함정**: 단시간 대량 호출(~4,000콜, 동시성 10) 직후 DART 가 호스트 수준에서
   연결을 리셋했다 (API 뿐 아니라 웹페이지도 HTTP 000). 일시 차단 또는 자정(KST) 점검으로 추정.
   → 벌크 측정은 **동시성을 낮추고(3 이하) 자정 전후를 피할 것**. 동시성 3으로는 연속 2회(각 ~3,000콜)
   재실행에도 차단이 없었다.

## 정직성 한계 — 지우지 말 것

- `J ≡ rm"공"` 은 실측된 경험적 등식이지 보장된 불변식이 아니다 (함정 6번). 이 기준선은
  "2025-08~2026-07 에 성립했다"는 사실을 고정할 뿐, 미래 성립을 보증하지 않는다.
- **"완전 수집"은 측정용 상향 설정에서만 성립한다** (`GONGSI_MAX_PAGES=150` + threshold 500 +
  per-chunk 15분). **출하 기본값(maxPages 100, threshold 1000, per-chunk ≤50초)으로는
  결산시즌 단일 일자 청크(20260401 = 136페이지)가 지금도 절단된다** — `truncated:true` 로
  정직 보고되므로 거짓 안심은 아니지만, 기본값으로 이 기간을 전수 수집할 수는 없다.
- **측정은 측정 시점의 dist(컴파일본)로 수행된다** (Codex 7차 치명 6). 이후 수집 파이프라인
  (`src/search/batch.ts` 등)을 고쳤다면 그 수치는 "고치기 전 코드"의 recall 이다 —
  파이프라인 변경 커밋 뒤에는 `npm run build` 후 재측정으로 재현을 확인하고 이 문서에 기록할 것.
  오프라인 회귀 테스트(recall-baseline.test.ts)는 픽스처의 내적 정합성만 보며, 현재 코드의
  행을 한 건도 수집하지 않는다.

## 재측정 절차

```sh
# 동시성을 낮춰 실행 (차단 방지) + 결산시즌 단일 일자 청크 대비 페이지 상한 상향.
# 소요 ~12분, 호출 ~3,300
GONGSI_CONCURRENCY=3 GONGSI_MAX_PAGES=150 node scripts/measure-recall-baseline.mjs > result.json
```

- J recall 이 100% 가 아니거나 창별 수치가 이 문서와 다르면 → **수집 파이프라인 회귀**. 원인 규명 전까지
  audit/batch 결과의 "누락 없음" 문구를 신뢰하지 말 것.
- 전체시장 창별 수치도 고정 기간이므로 재현되어야 한다 (다르면 회귀 신호).
