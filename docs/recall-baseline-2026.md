# 1년 recall 기준선 (2026-08-13 실측)

> 함정 8번 해소: "recall 관련 판단은 1년 이상 윈도우로만 확정한다."
> 참고 MCP 는 10일 윈도우로 "recall 100%"를 두 번 선언했다가 두 번 뒤집혔다.
> 이 문서 이전까지 우리 전수성 근거도 2주×2구간(28일)뿐이었다.

## 결론

| 항목 | 결과 |
|---|---|
| **J 수집 recall (1년)** | **30,063 / 30,063 = 100%** — 창별 6개 전부 수집=신고, partial·절단·실패 0 |
| **J → rm"공"** | J 30,063건 **전부** "공" 마커 보유 — 1년 완전 검증 |
| **rm"공" → J (역방향)** | 수집된 전체시장 139,586건(85.3%) 범위 내 반례 **0건** — 완전 검증은 재측정 대기 |
| 종전 측정과 대조 | 2026-07-31 측정 "1년 J = 30,063건"과 **정확히 일치** (재현성 입증) |

## 방법

- 스크립트: `scripts/measure-recall-baseline.mjs` — **프로덕션 수집 경로(`collectAdaptive`) 그대로** 사용.
  별도 수집기를 만들어 재면 우리 코드의 recall 이 아니라 측정기의 recall 을 재게 된다.
- 기간 고정: **2025-08-01 ~ 2026-07-31**. `rcept_dt`(접수일)는 과거로 소급 추가되지 않으므로
  이 기간의 수치는 언제 재측정해도 같아야 한다 → 회귀 기준선으로 성립.
- 창 구성: 2개월 × 6개 (corp_code 없는 검색·측정은 3개월 초과 시 status 100 — 함정 10번).
- 대조 기준: 각 창에서 DART 가 신고한 `total_count` 합계 vs 실제 수집한 고유 `rcept_no` 수.
- 회귀 테스트: `test/recall-baseline.test.ts` + `test/fixtures/recall-baseline-2026.json` (오프라인 —
  기준선 계약을 고정. 실제 재측정은 스크립트 수동 실행).

## 정직성 한계 — 지우지 말 것

1. **역방향(공∉J) 검증은 85.3% 범위다.** 전체시장 수집에서 결산시즌 대형 청크 6개가 per-task
   180초 타임아웃으로 실패했고, `partial_results=true` 로 정확히 보고됐다 (이 방어 자체는
   korean-dart-mcp 피드백 §2-1 ②가 경고한 사고 유형의 방어가 실전 작동한 첫 사례).
   실패 청크 구간의 J 건 10,553개가 전체시장 수집본에 없는 것도 같은 원인이며 파이프라인 결함이 아니다.
2. **재측정 중 발견된 신규 함정**: 단시간 대량 호출(~4,000콜, 동시성 10) 직후 DART 가 호스트 수준에서
   연결을 리셋했다 (API 뿐 아니라 웹페이지도 HTTP 000). 일시 차단 또는 자정(KST) 점검으로 추정.
   → 벌크 측정은 **동시성을 낮추고(3 이하) 자정 전후를 피할 것**. 참고 아카이브 플레이북
   §2.6 "공공 API 에서는 병렬화 유혹을 참는 것이 정답"과 일치하는 실측.
3. `J ≡ rm"공"` 은 실측된 경험적 등식이지 보장된 불변식이 아니다 (함정 6번). 이 기준선은
   "2025-08~2026-07 에 성립했다"는 사실을 고정할 뿐, 미래 성립을 보증하지 않는다.

## 재측정 절차

```sh
# 동시성을 낮춰 실행 (차단 방지). 소요 ~15분, 호출 ~2,300
GONGSI_CONCURRENCY=3 node scripts/measure-recall-baseline.mjs > result.json
```

- J recall 이 100% 가 아니거나 창별 수치가 이 문서와 다르면 → **수집 파이프라인 회귀**. 원인 규명 전까지
  audit/batch 결과의 "누락 없음" 문구를 신뢰하지 말 것.
- 전체시장이 완전 수집되면(issues 0) 역방향 검증을 "완전"으로 갱신하고 픽스처·이 문서를 업데이트.
