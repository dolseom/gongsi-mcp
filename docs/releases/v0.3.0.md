# gongsi-mcp 0.3.0

작성 2026-09-14 · **npm 배포 2026-09-15** (태그 `v0.3.0` = `3efbf50`, publish run 34983816217, 레지스트리 tarball sha256 `a11bd084…468f` = 검토본과 바이트 동일).
실행 중인 버전은 `server_info` 의 `version` 으로 확인하세요.

## 요약

- 도구 16 → **17개** — 미공시 탐지 결과의 전문을 이어 읽는 `read_detection_result` 추가.
- `detect_undisclosed_transactions` 의 첫 응답이 **크기 예산 안의 요약**으로 바뀌었습니다
  (전체 결과가 22만 자~1MB 라 MCP 호스트가 전달하지 못하던 문제). 전문은 요약의 `detail_access.result_id` 를
  `read_detection_result` 의 입력 `result_id` 에 넣어 읽습니다.
- `check_disclosure_duty` 는 입력이 일부 빠져도 오류로 끝내지 않고 **계산할 수 있는 부분을 돌려줍니다**.
  확정하지 못한 계산은 `missing_inputs`·`components` 로 표시합니다 — 예: 금액·자본 등 대상 요건이 충족된 경우,
  이사회 의결일이 없으면 대상 판정 `verdict: required` 와 기한 `components.deadline.status: insufficient_data` 가 함께 나옵니다
  (의결일이 없다는 것만으로 `required` 가 되지는 않습니다).
- 미공시 탐지 정확도 개선 다수 — 아래 목록.

**버전 번호**: 0.x 에서는 minor 가 호환성 변경을 알리는 자리입니다. 탐지 응답의 최상위 형식, 누락 입력의
응답(오류 → 판정), Node.js 하한이 바뀌었으므로 0.2.1 이 아니라 0.3.0 입니다. npm 범위 `^0.2.0` 은 0.3.0 을
포함하지 않습니다.

## 업그레이드 시 확인할 것 (호환성)

### 1. Node.js 22.13 이상 필요

`engines.node` 가 `>=22.5` → **`>=22.13`**. 내장 `node:sqlite` 를 `--experimental-sqlite` 플래그 없이 쓰는 하한입니다.
22.5~22.12 에서 쓰던 환경은 Node 를 먼저 올리세요.

### 2. MCP 클라이언트 재시작

이미 떠 있는 서버 프로세스는 옛 코드입니다. 업그레이드 뒤 MCP 클라이언트(또는 해당 MCP 서버 연결)를 다시 시작해야
17번째 도구·바뀐 도구 설명·서버 지침(`initialize` 의 `instructions`, 0.3.0 신설)이 적용됩니다.
실행 중인 버전은 `server_info` 의 `version` 으로 확인합니다. 특정 버전을 지정하려면 `npx -y gongsi-mcp@0.3.0`.

### 3. `detect_undisclosed_transactions` — 응답 형식 변경 ⚠️ 호환성 깨짐

0.2.0 은 탐지 결과 전체를 최상위 응답으로 돌려줬습니다. 0.3.0 의 최상위 응답은 **요약**입니다
(직렬화 기준 24,576바이트 제품 예산 — 호스트 한도가 아니라 여유 있게 잡은 상한).

| 필드 | 내용 |
|---|---|
| `detail_access` | `result_id`(32자리 16진수) · `expires_at` · `total_chars` · `available_sections`(+`_total`) · `how_to_read` · `lifetime_note` |
| `scope` / `continuation` | 원천 공시·판정 시점 / 이어보기 상태(`complete`·`token`·`stalled` 등) |
| `action_items_preview` | 조치 필요 판정 **최대 5건**(크기 예산 때문에 더 적을 수 있음) + `total`·`shown`·`omitted` |
| `summary` · `coverage_undetectable` · `required_warnings` | 집계 · 실질 미검토 범위 · 고정 경고 |
| `caveats_and_notes` | caveat·note **총수**와 항목당 **최대 200자** preview(예산이 모자라면 preview 부터 줄어듦) — 전문은 section 조회 |
| `details_required: true` · `summary_incomplete` | 이 응답이 원본의 일부라는 표시 |

`result_id` 는 탐지 응답의 최상위 필드가 아닙니다 — **`detail_access.result_id`** 에 있습니다.

**전체 결과 읽기 — `read_detection_result`**

- 입력: `result_id`(필수 — 탐지 응답의 `detail_access.result_id` 값을 그대로) · `section`(선택, `detail_access.available_sections` 중 하나 — 생략하면 전체) · `offset`(UTF-16 코드 단위, 기본 0) · `limit`(기본·최대 8,000).
- 응답의 `next_offset` 을 다음 호출의 `offset` 에 그대로 넣어 **`next_offset` 이 `null`(`complete: true`)이 될 때까지** 반복합니다.
  서버가 예산에 맞춰 요청보다 짧게 줄 수 있지만 `next_offset` 은 항상 전진합니다.
- 조각 `text` 를 순서대로 이어붙이면 엔진 원본 JSON 문자열과 정확히 같습니다. 중간 조각은 단독으로 유효한 JSON 이 아닐 수 있습니다.
- 키가 필요 없고 탐지를 다시 돌리지 않습니다.

**보관 수명과 회수**

- 상세는 **서버 프로세스 메모리에만** 보관됩니다 — 디스크에 쓰지 않습니다.
- 한 결과의 수명 **30분**. 보관 **최대 4건** — 넘으면 가장 오래된 결과부터 회수. 1건 16MiB·합계 32MiB 한도.
- 만료·회수·서버 재시작 뒤에는 `result_unavailable` (서버가 셋을 구분하지 못합니다) → 탐지를 다시 실행하세요.
- 결과가 보관 한도를 넘으면 `resource_limit` — 탐지는 수행됐으므로 오류 응답에 요약을 동봉합니다.
- 요청을 **취소**하면 결과를 보관하지 않고 기존 결과도 회수시키지 않습니다. 단 이미 시작된 DART 조회는 계속될 수 있어 호출 한도를 씁니다.

**전체 결과(상세) 안의 변경** — 0.2.0 이후 판정 배열·어휘가 추가됐고, 두 가지는 기존 필드 위치에 영향을 줍니다.

- `action_items`: 조치가 필요한 판정을 상태별 배열을 가로질러 앞에 모은 목록(각 항목에 원래 배열 이름 `source`). 기존 배열은 그대로입니다.
- 닫힌 판정 배열에서 **모든 항목의 값이 같은 필드**는 항목에서 빠지고 `<배열이름>_shared` 에 한 번만 실립니다(`status` 는 올리지 않음). 항목별로 그 필드를 읽던 파서는 `_shared` 도 보세요.

### 4. `detect_undisclosed_transactions` — 입력·실행 방식

- 새 입력 `continuation_token`: 한 호출에서 끝나지 않으면 응답의 토큰을 **같은 인자**에 넣어 다시 부르면 안 본 회사부터 이어 봅니다.
  토큰이 만료·불일치면 `continuation_invalid`(토큰 없이 처음부터 다시 실행). 더 불러도 진전이 없으면 `stalled: true`.
- `continuation.complete: true` 는 **재호출로 진전할 수 있는 검색 반복이 끝났다**(`continuation.incomplete_reasons` 가 비었다)는
  뜻일 뿐, 모든 판정이 확인됐다는 뜻이 아닙니다. 조인 실패·판정 불가·유형 미상 보류 같은 미판정과 `coverage` 의 미검토 범위는
  다시 불러도 그대로 남을 수 있고, 첫 응답은 요약이라 읽지 않은 상세도 남습니다.
  상세는 `complete: true` 를 낸 **마지막 호출** 응답의 `detail_access.result_id` 로 읽으세요 — 앞 호출이 준 `result_id` 는 그 시점의 부분 결과입니다.
- 호출당 시간 예산 50초 — 진행 중인 조회는 끝내되 새 조회를 시작하지 않고 **부분 결과임을 명시**합니다
  (못 본 항목의 사유 문구 `time_budget_exceeded`, `continuation.incomplete_reasons`, 상세의 `diagnostics.budget`).
  원천 공시조차 못 받은 경우만 `deadline_exceeded` 오류.
- 환경변수 `GONGSI_TIME_BUDGET_MS`(선택): 예산을 **낮추기만** 합니다(5,000~50,000ms 로 조정). 재현·진단용.

### 5. `check_disclosure_duty` — 누락 입력의 응답 변경 ⚠️ 호환성 깨짐

- 0.2.0 은 이사회 의결일·상장 여부·분기말 등이 없으면 `invalid_argument` 로 응답 전체를 거절했습니다.
  0.3.0 은 계산 가능한 부분을 돌려주고, 확정하지 못한 계산을 필드로 알립니다. **`verdict` 는 계산된 부분에 따라 달라집니다** —
  예: 금액·자본 등 대상 요건이 충족된 경우(금액 ≥ 기준금액), 이사회 의결일·상장 여부가 없으면 `verdict: required` · `components.duty.status: evaluated` ·
  `components.deadline.status: insufficient_data`(`missing_fields` 에 `boardDate`·`listing`). 금액·자본까지 없으면 대상 판정도 `insufficient_data` 입니다.
  - `missing_inputs` — 항목마다 `purpose`(`duty` 대상 판정용 / `deadline` 기한 계산용)
  - `components.duty.status` · `components.deadline.status` — `evaluated` / `insufficient_data` / `not_applicable`
  - `review` — 결론 · 적용 전제 · 핵심 근거 · 미확인 사항 · 다음 행동
- 기한을 계산하지 못하면 `deadline`·지연·과태료·자진시정 필드를 **만들지 않습니다**.
- 기한만 계산하는 유형(`omnibus_financial`·`goods_services_reduced`·`group_status`)은 기한 입력이 없으면 `verdict: insufficient_data`.
- 비상장사 중요사항 지분변동에서 `shareholderType` 이 없으면 대상 판정만 하고 기한은 미확정(종전 오류).
- 대상이 미확정인데 지연·과태료를 계산한 경우 "공시 대상으로 확정될 경우의 값"이라는 note 가 붙습니다.
- **제공했지만 잘못된 값**(실존하지 않는 날짜·분기말이 아닌 날짜·공시일 역전)은 종전대로 오류입니다.
- 연동 코드가 "오류가 나면 입력 부족"으로 처리했다면 `verdict` 하나가 아니라 `components` 의 계산별 상태와 `missing_inputs` 를 확인하도록 바꾸세요.

### 6. 그 밖의 표면 변경

- 새 오류 코드: `deadline_exceeded` · `continuation_invalid` · `resource_limit` · `result_unavailable`.
- `check_j004_consistency` 설명 정정 — **접수된 제출본(접수번호)** 점검이며 미제출 초안 파일은 읽지 못합니다(동작 변경 없음).
- 도구 설명을 줄이고 공통 원칙(되묻기·답변 순서·범위 밖 질문)을 서버 지침으로 옮겼습니다.

## 미공시 탐지 개선 (0.2.0 이후)

- 거래 한 건의 의무자 둘을 따로 판정: 자금 **대여회사** 관점, 상품·용역 **매입회사**·유가증권 **매도회사** 관점 — 기준금액은 각자의 자본.
- 상품·용역 (5) 총괄 매트릭스를 판정에 통합, (6) 주요 내역에 같은 쌍이 있어도 (5)가 더 크면 큰 값으로 판정(두 값 동봉).
- 국외 계열회사 상대 거래를 후보에서 분리(`not_applicable_foreign_affiliate`, 법 §26①·고시 §2③2호).
- "공시 존재"는 공시 원문의 **거래상대방까지 확인한 것만** — 확인 못 하면 판정 보류.
- 보고서명만으로 유형을 알 수 없는 J001 은 후보로 단정하지 않고 원문 상대방·거래대상으로 판정.
- 동명 법인은 법인등록번호로만 확정, 포털 조인 0건이어도 모집단 유지 + 법인등록번호 자동 채움.
- J004 서식 변형 대응: 재무현황 회사명 열 `소속회사명`(실물 40문서 중 39), 2열 단위 캡션.
- 헤더 승격·열 수 불일치를 진단에 계측.

## 알려진 한계

- 탐지 결과는 전부 **후보**입니다. 상품·용역은 상대방 지분 요건(동일인·친족 20%)을 확인하지 못해 조건부 후보에 머뭅니다.
- 담보·채무보증·부동산 임대차·기타 자산 거래 유형은 아직 대조하지 않습니다.
- 기준미달 산술은 J004 시점의 자본 스냅샷 기준이라 거래 시점 자본 변동을 반영하지 못합니다.
- 기업집단포털 소속회사 수집이 페이지 상한에서 표시 없이 끝날 수 있는 경로가 남아 있습니다.
- 탐지 상세는 30분·최대 4건·프로세스 메모리 한정 — 오래 걸리는 검토는 탐지를 다시 실행해야 할 수 있습니다.
- 취소해도 이미 시작된 DART 조회는 계속됩니다. 비-Windows·다른 호스트의 취소 타이밍은 검증하지 않았습니다.
- 자연어 종단 평가는 합성 질문 기반이며 실사용 검증이 아닙니다. 집단 전수 탐지 같은 질문은 응답까지 수 분이 걸릴 수 있습니다(대부분 모델이 답을 쓰는 시간).
- 공휴일 데이터는 2026·2027년분만 공식 공고와 대조했습니다.
